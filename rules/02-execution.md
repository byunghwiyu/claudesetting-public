# 02. 작업 실행 규칙

## 사전 정리 (Step 0)
- 구조 변경에 필요한 정리만 변경 범위 안에서 수행한다. 관련 없는 미사용 코드·로그는 보고만 한다.

## 단계적 실행
- 복수 파일 변경은 독립적으로 검증 가능한 **작업 단위(Phase)**로 분리한다. 승인 파일 목록·파일별 목적·검증 방법·중간 확인 지점을 시작 계획에 포함한다.
- 승인 범위 안에서 필수 검증을 통과하면 결과를 보고하고 다음 단위로 진행한다. 재승인·중간 확인·엄격 모드 조건은 06-rubric.md의 공통 하네스 계약을 따른다.
- 5파일 초과 단위는 묶는 이유를 시작 승인 요청에 포함한다. 엄격 모드에서는 단위당 최대 5파일이며 매 단위 검증 후 다음 단위 승인을 받는다.
- 대규모 변경 전 **버티컬 슬라이스** 방식으로 작은 단위부터 검증
- 독립 작업의 병렬 실행·서브에이전트 사용은 사용자가 허용한 경우에만 수행한다. 파일 수가 병렬 실행 권한을 부여하지 않는다.
- 허용되지 않은 경우 메인 에이전트가 검증 가능한 작업 단위로 나누어 순차 수행한다.
- 목록 밖 파일 수정과 계획에 없던 중요 변경은 구현 전에 재승인받는다. 첫 단위 시범 결과·실제 런타임 검증·구조 변경 지점의 중간 확인과 엄격 모드는 공통 하네스 계약을 따른다.

## 작업 결정 기록

다음 중 하나에 해당하면 작업 디렉터리에 `implementation-notes.md`를 유지한다.

- 길거나 해석 여지가 큰 명세
- 두 개 이상 Phase, 5파일 초과 변경 또는 구조 변경
- 사용자 동작, 데이터 구조, 공개 API, 저장 방식, 테스트 전략에 영향을 주는 결정
- 명세와 구현 사이의 의도적인 편차

설계 결정, 편차, 트레이드오프, 미결 질문만 기록한다. 변수명·단순 포매팅처럼 동작에 영향 없는 선택은 기록하지 않는다.
기존 기록을 보존하고 필요한 항목만 추가·갱신한다. 기록을 이유로 매번 질문하지 않으며 승인 범위 안에서는 진행한다.
되돌리기 어렵거나 사용자 경험에 큰 영향을 주는 결정은 구현 전에 확인받는다.
공개 배포를 준비할 때는 개인 경로·비공개 요구사항이 포함된 기록을 공개 저장소 밖에 둔다.

## 완료 기준 (필수 검증)
코드 작성/수정 후 반드시 아래 순서를 실행할 것. 모든 검사 통과 전까지 완료 보고 금지.

1. `dotnet build` → 컴파일 에러 0 확인
2. `dotnet format --verify-no-changes` → 포매팅 위반 확인
   - 이번 변경의 위반은 변경 파일로 범위를 제한해 교정하고 1번부터 재실행한다. 관련 없는 기존 위반은 별도로 보고한다.
3. 성공 로그는 생략하고 검사 결과를 짧게 보고한다. 미실행·실패한 검사를 통과로 보고하지 않는다.

#### 비-.NET 프로젝트
- Node/TS: `npm run build` (또는 `tsc --noEmit`) → `npm run lint`
- Python: `ruff check .` → `pytest` (테스트 존재 시)
- 마크다운/설정/문서: 빌드 대상이 아니며 한글 인코딩, 링크, 구조 일관성을 검증한다. 설정은 사용 가능한 파서로 구문도 확인한다.
- 프로젝트 자체 검증 명령이 있으면 위 기본값보다 우선한다.
- 위 3단계 자동 교정 루프 동일 적용

> **목표 기반 실행 원칙**: "무엇을 하라"보다 **성공 기준**을 명시할 것.
> 예: "버그 수정해" → "재현 테스트를 작성하고 통과시킬 것"
> 예: "검증 추가해" → "잘못된 입력 테스트를 작성하고 통과시킬 것"

### 자동 교정 루프
- 이번 변경으로 발생한 에러는 승인 범위 안에서 수정 후 재검사한다. 기존 오류나 검사 도구 부재는 구분해 보고한다.
- 포매팅 수정은 변경 범위에 한정하며, 관련 없는 파일까지 자동 교정하지 않는다.
- 재시도마다 실패 원인과 새 가설을 확인한다. 같은 오류가 2회 반복되면 접근을 바꾸고, 근거 없이 같은 수정을 반복하지 않는다.
- **3회 재시도 후에도 에러가 해결되지 않으면** 시도 내역과 함께 사람에게 보고.

### Unity 빌드 주의
- `dotnet build`는 Unity Editor 빌드와 결과가 다를 수 있음.
- 빌드 훅을 설치·등록한 환경에서는 해당 훅의 검사 범위를 먼저 확인한다. 훅 파일이 있어도 실제 앱에 등록됐는지 확인하기 전에는 자동 검증이 동작한다고 가정하지 않는다.
- 훅이 수정 파일만 포맷 검사했다면 프로젝트 전체 포맷 통과로 보고하지 않는다. 실패 진단을 확인하고 승인 범위 안에서 교정·재검사한다.
- CLI 빌드 통과 후에도 "Unity Editor에서 별도 확인 필요"를 명시할 것.
- Unity Test Runner 사용 시: `unity -batchmode -runTests -projectPath .`

### Unity 프로젝트 매핑 — 해당 프로젝트가 사용하는 경우

프로젝트에 `codex.project-map.json`이 있으면 문서 경로와 갱신 트리거를 읽고 해당 매핑을 재사용한다.

- Session / Progress / Decisions / Battle Reference 경로와 `qa.docTriggers`를 실제 프로젝트 기준으로 확인한다.
- 매핑이 없는 프로젝트에는 기존 문서 구조를 먼저 확인한다. 별도 승인을 받기 전까지 새 구조를 강제하지 않는다.
- 매핑 템플릿과 전문 에이전트는 이번 핵심 공개본에 포함되지 않는다. 설치되지 않은 템플릿·스킬을 호출했다고 보고하지 않는다.
